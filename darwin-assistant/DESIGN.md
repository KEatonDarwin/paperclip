## Goal

Kevin can say "monitor X" in plain language and JARVIS creates a cheap scheduled prompt-check agent. The monitor runs on a cadence for a bounded window, records pass/fail/error history, surfaces state changes through cockpit notifications, appears in an Overwatch-style cockpit UI, contributes to Morning Debrief, and self-cleans when its run window ends.

Hard constraints:

- No API keys for model calls. Use the existing local CLI adapter seam only.
- Do not introduce external migrations. Keep SQLite DDL module-local with `CREATE TABLE IF NOT EXISTS`, matching `src/hopper.ts`, `src/thread-todos.ts`, and `src/notifications.ts`.
- Do not touch production databases or live deploy scripts.

## Runner Mechanism Decision

Use one persistent cockpit worker thread per monitor:

```text
monitor id 42 -> cockpit:monitor-42
```

Each run posts a normal cockpit message to that thread through the existing message/queue path, not a direct `runClaude()` call. Before the first run, the monitor module creates or loads the conversation and calls `setThreadModelOverride(conversation.id, monitor.adapter, monitor.model)`. The default is:

```text
adapter: claude
model: claude-haiku-4-5-20251001
```

Rationale:

- Full tool access: the check can use existing JARVIS tools, local file reads, curl, sqlite reads, etc. through the same runtime as a normal thread.
- No new model invocation path: model calls remain behind `processMessage()` and the adapter seam in `agent.ts`, preserving the no-API-key rule.
- Session continuity: the monitor thread can accumulate context over daily checks without shoving the full run history into every prompt.
- Queueing and mutex safety: if a monitor thread is still running, `/threads/:ext/messages` queues the next run instead of double-running.
- Cockpit visibility: Kevin can open the thread if he wants the raw check transcript, but the main UI reads structured run records.

Deviation from the initial recommendation: the scheduler should not call `processMessage()` directly unless it reuses the same helper shape as the REST message route. Prefer a small internal `sendThreadMessage()` helper extracted from the API route so scheduler, Hopper, and HTTP ingress share queue/error behavior. If extraction is too large for v1, the scheduler can call `processMessage()` with the same busy handling as the route, but that is second-best.

## Prompt Contract

Each run message is generated by the monitor scheduler and includes:

- monitor title and natural-language check prompt,
- expected status definitions,
- current run timestamp and cadence/window metadata,
- instruction to do read-only inspection unless Kevin explicitly authorized otherwise,
- a strict final-line JSON envelope.

Required final line:

```json
{"status":"pass|fail","summary":"...","detail":"..."}
```

Parsing rule:

- Read the assistant turn returned by `/threads/:ext/messages/:message_id`.
- Parse the last non-empty line as JSON.
- `status` must be `pass`, `fail`, or `error`; model may only emit `pass` or `fail`.
- Missing/invalid JSON becomes `error` with `summary = "Monitor reply did not contain a valid result envelope"`.
- Persist the raw assistant turn id/content excerpt for debugging.

## Backend Schema

New module: `src/monitors.ts`.

```sql
CREATE TABLE IF NOT EXISTS monitors (
  id                    INTEGER PRIMARY KEY AUTOINCREMENT,
  title                 TEXT NOT NULL,
  prompt                TEXT NOT NULL,
  source_thread_ext     TEXT,
  monitor_thread_ext    TEXT NOT NULL UNIQUE,
  adapter               TEXT NOT NULL DEFAULT 'claude',
  model                 TEXT NOT NULL DEFAULT 'claude-haiku-4-5-20251001',
  cadence_minutes       INTEGER NOT NULL,
  starts_at             TEXT NOT NULL DEFAULT (datetime('now')),
  ends_at               TEXT,
  next_run_at           TEXT NOT NULL,
  status                TEXT NOT NULL DEFAULT 'active'
    CHECK (status IN ('active','paused','expired','archived')),
  severity              TEXT NOT NULL DEFAULT 'medium'
    CHECK (severity IN ('low','medium','high','critical')),
  last_outcome          TEXT
    CHECK (last_outcome IN ('pass','fail','error') OR last_outcome IS NULL),
  last_state_key        TEXT,
  last_state_changed_at TEXT,
  created_at            TEXT NOT NULL DEFAULT (datetime('now')),
  updated_at            TEXT NOT NULL DEFAULT (datetime('now')),
  archived_at           TEXT
);

CREATE INDEX IF NOT EXISTS idx_monitors_status_next_run
  ON monitors(status, next_run_at);

CREATE TABLE IF NOT EXISTS monitor_runs (
  id                 INTEGER PRIMARY KEY AUTOINCREMENT,
  monitor_id         INTEGER NOT NULL REFERENCES monitors(id),
  scheduled_for      TEXT NOT NULL,
  started_at         TEXT,
  finished_at        TEXT,
  status             TEXT NOT NULL DEFAULT 'queued'
    CHECK (status IN ('queued','running','pass','fail','error','cancelled')),
  message_id         TEXT,
  assistant_turn_id  INTEGER,
  summary            TEXT,
  detail             TEXT,
  raw_reply          TEXT,
  error              TEXT,
  created_at         TEXT NOT NULL DEFAULT (datetime('now'))
);

CREATE INDEX IF NOT EXISTS idx_monitor_runs_monitor_created
  ON monitor_runs(monitor_id, created_at DESC);
```

Notes:

- `monitors.status = expired` means the monitor window ended and no more runs dispatch.
- `archived` is manual cleanup after Kevin no longer wants it visible.
- Keep history by default; "self-cleaning" means stop dispatching and optionally hide expired cards by default, not delete evidence immediately.
- A later retention sweep can delete raw replies for archived monitors older than N days, but v1 should not silently delete audit history.

## Scheduler Semantics

New worker: `src/monitor-worker.ts`.

Tick interval: 60 seconds, same class as `checkin-worker.ts`.

On each tick:

1. Mark active monitors expired when `ends_at IS NOT NULL AND ends_at <= now`.
2. Select a bounded batch of active monitors due at `next_run_at <= now`.
3. For each due monitor:
   - create a `monitor_runs` row with `status='queued'`,
   - ensure the persistent monitor thread exists,
   - force `setThreadModelOverride()` to monitor adapter/model,
   - mark run `running`,
   - post the generated run prompt to the monitor thread,
   - poll the message result until complete or timeout,
   - parse final JSON and update the run to `pass`/`fail`/`error`,
   - advance `next_run_at` by cadence from the prior scheduled time, not from finish time, to avoid drift.

Timeouts:

- Use a run timeout independent of the model idle timeout, e.g. 20 minutes.
- Timeout outcome is `error`.
- Do not schedule catch-up storms. If a monitor is overdue by many intervals, run once and set the next due time to the first future cadence boundary.

Cadence examples:

- "daily for a week": `cadence_minutes=1440`, `ends_at=starts_at + 7 days`.
- "every hour until tomorrow": `cadence_minutes=60`, `ends_at=tomorrow`.
- "weekdays at 8am" can be v2. v1 supports fixed minute cadence only.

## State-Change Notifications

Mirror watchdog/Overwatch behavior: notify on meaningful state changes, not every run.

State key:

```text
<last_outcome>:<summary-normalized-or-empty>
```

Notification rules:

- `pass -> fail`: warning/error notification depending on monitor severity.
- `fail/error -> pass`: success notification.
- `pass -> error`: warning notification.
- repeated same fail/error: no new notification; visible in run history only.
- expiry: one info notification, "Monitor ended: X", with link to the monitor page.

Implementation:

- Store `last_outcome`, `last_state_key`, and `last_state_changed_at` on `monitors`.
- Use `createNotification()` with `source='Monitor'` and link `/monitors/<id>` or `/monitors`.

## API Surface

Add routes to `src/handlers/api-v1.ts`.

```text
GET    /monitors?status=active|paused|expired|archived|all
POST   /monitors
GET    /monitors/:id
PATCH  /monitors/:id
POST   /monitors/:id/run-now
POST   /monitors/:id/pause
POST   /monitors/:id/resume
POST   /monitors/:id/archive
GET    /monitors/:id/runs?limit=50
```

`POST /monitors` body:

```json
{
  "title": "Health dashboard status",
  "prompt": "Check whether health.thedarwinhub.com is returning 200 and whether today's sync completed.",
  "cadence_minutes": 1440,
  "duration_days": 7,
  "severity": "high",
  "adapter": "claude",
  "model": "claude-haiku-4-5-20251001",
  "source_thread_ext": "cockpit:..."
}
```

`run-now`:

- If no run is active for the monitor, schedule one immediately.
- If a run is already active, return `202` with the active `run_id`.

Plain-language creation can be v1.5:

- Add a `monitors` tool so JARVIS can interpret "monitor X daily for a week" inside a normal conversation and call `createMonitor()`.
- The actual parser can initially be model-side through JARVIS; the backend API should stay explicit and predictable.

## Morning Debrief Hook

Extend `src/briefing.ts` signal with monitor activity:

- monitors that changed state in the last `OVERNIGHT_HOURS`,
- currently failing/error active monitors,
- monitors that expired overnight.

Add a short section inside the existing debrief prompt material rather than creating a sixth output section. Recommended wording:

```text
=== COCKPIT MONITORS (last 16h + currently failing) ===
- [fail/high] Health dashboard status — sync has not completed since 2am (last run 06:00)
- [recovered] Ongage double-run — passing again
```

In the deterministic fallback, include failing monitors under `Needs your call` only when their severity is `high` or `critical`; otherwise keep them in the autonomous-work summary.

## Self-Cleaning

Self-cleaning means:

1. monitors stop scheduling when `ends_at` passes,
2. active UI hides expired monitors by default,
3. one expiry notification is sent,
4. Morning Debrief can mention expirations from the overnight window,
5. archived monitors remain queryable for audit but leave the main view.

Do not hard-delete monitor/run rows in v1. This matches Kevin's "nothing gets dropped" posture and preserves the debugging trail.

## Risks / Open Decisions

- **Polling the message result:** the scheduler needs a non-HTTP internal equivalent of `/threads/:ext/messages/:messageId` or a small helper that waits for the target assistant turn. Implement this once; do not duplicate ad hoc polling logic in the worker.
- **Tool blast radius:** monitor prompts must default to read-only inspection. The underlying JARVIS runtime has powerful tools, so the prompt contract and monitor tool docs must say checks do not mutate unless Kevin explicitly asked.
- **Cadence parser:** natural-language cadence parsing can stay in JARVIS/tool layer for v1. Backend receives explicit `cadence_minutes` and `ends_at`.
- **Haiku model id:** current adapter list includes `claude-haiku-4-5-20251001`; use that exact id unless Kevin changes the model catalog.
- **Thread noise:** persistent monitor threads will accumulate many run prompts. That is intentional for audit/session continuity. The UI should make the run table the primary surface so Kevin is not forced into the raw thread.

## Summary Recommendation

Build Cockpit Monitors as a thin durable scheduler and UI over the existing cockpit thread/runtime substrate. Do not create a separate agent runner. A monitor is a durable record plus a persistent cheap-model thread; each scheduled run is just a normal queued message whose final JSON envelope is parsed into `monitor_runs`. This preserves no-API-key execution, gives checks full tool access, uses existing model overrides and queueing, keeps Kevin's audit trail, and makes the Overwatch-style UI mostly a read surface over `monitors` and `monitor_runs`.
